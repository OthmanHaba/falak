# Backups: encryption, keys and restore drills

Every backup Falak takes — a database dump, a Redis / Valkey snapshot, a volume archive — is compressed and encrypted
on the server before it leaves it, with a key of its own. There is no unencrypted option. Schedules can also restore
their latest backup into a throwaway instance on a regular basis and check it (restore drills). Plan:
`docs/plans/V0_10_PRODUCTION.md` §4.

## The file format: FKB1

`agent/internal/backupcrypt`. The data is compressed with zstd, then encrypted with AES-256-GCM in 64 KiB segments
(the STREAM construction), so a backup of any size streams through the agent in constant memory.

```
header   "FKB1" | version 1 | cipher 1 (AES-256-GCM) | compression 1 (zstd) | key mode (1 cp, 2 age)
         | segment size u32 | key id (u8 length + bytes) | wrapped key (u16 length + bytes) | base nonce (12 bytes)
segment  length u32 | AES-256-GCM(compressed data)          (length + 16 bytes; 1 ≤ length ≤ segment size)
trailer  0x80000028 | AES-256-GCM(data length u64 | SHA-256 of the data)
```

- The encryption key is HKDF-SHA256(data key, salt = base nonce, info `falak backup FKB1`).
- Segment *i* (the trailer included) uses nonce = base nonce XOR *i* (low 8 bytes), with the first byte flipped for
  the trailer, and AAD = SHA-256(header) | kind. So: any change to the header fails every segment; dropped, repeated
  or reordered segments fail (counter); a file cut short fails (only the trailer may end it); bytes after the
  trailer fail.
- The trailer authenticates the length and SHA-256 of the **uncompressed** data (the dump, the RDB, the tar stream).
  The reader checks them at the end of the stream; the control plane also records them (`plaintext_sha256`) and the
  agent compares on every restore. The stored file's own SHA-256 (`sha256`) is checked before anything is decrypted.
- **Restores verify first.** The agent downloads the file into a staging directory on the volume store (free space
  checked against the recorded size), checks the stored file's SHA-256 (required), then decrypts the whole file to
  nothing — every segment, the trailer, the recorded plaintext SHA-256 — and only then streams it into `falak-db
  restore`. Volume restores do the same before unpacking. If reading fails while it streams (a disk error), the
  restore's `docker exec` is killed so falak-db never takes the early end for a complete dump.
- PostgreSQL restores load into a scratch database swapped in only on success, and Redis / Valkey snapshots replace
  `dump.rdb` only once complete. MySQL / MariaDB restores load into the target database directly (MySQL has no
  `RENAME DATABASE`): with the verification pass, only an error of the engine itself (a statement it refuses) can
  leave a partial restore; restore into a new database to keep the current one untouched.

Object keys end in `.sql.zst.fkb`, `.rdb.zst.fkb` or `.tar.zst.fkb`.

## Keys

Every backup has a random 32-byte **data key**. Who holds it is chosen per schedule (`encryption_mode`):

| | `cp` (default) | `customer` |
|---|---|---|
| Generated by | the control plane | the agent, on the server |
| Stored | on the backup row, sealed under the organization's data key (Kernel `Sealer`, AAD `("backup", organization id, backup id)`): it opens for no other row or organization | in the file's header, encrypted with [age](https://age-encryption.org) to the schedule's X25519 recipient (`age1…`) — a complete age file, `age -d` opens it |
| Reaches the agent | inside the command payload (sealed at rest in `fleet_commands`, masked in output, kept in memory only); the payload forgets it (`[forgotten]`) once the command settled, and the fleet sweep does it for settled commands a listener missed and commands stuck past their timeout (`x-falak-forget-secrets` in the command schemas) | never leaves the server |
| Restore | automatic | asks for the age private key (`AGE-SECRET-KEY-1…`): sent once in the restore command, forgotten when it settled, never stored, or offline with `falak-restore` |
| Restore drills | yes | no: Falak can't decrypt them (recorded as skipped) |

Manual backups ("Back up now"), moves and clones of volumes always use `cp` keys. A customer-held schedule never falls
back to them: without a valid recipient its backups fail. The age identity typed for a restore is never flashed into
the session with validation errors (`dontFlash`, the dialog posts JSON). The organization's data key is
wrapped by the KEK (the key hierarchy, `docs/INSTALL.md`); deleting an organization deletes its data keys, after which
its `cp` backups can't be opened by Falak — export the keys you want to keep first.

Customer-held keys: create one with `age-keygen -o falak-backups.key` (keep that file safe, offline), and paste the
`# public key: age1…` line into the schedule.

### Exporting a key ("Export backup key")

`POST /databases/backups/{backup}/key` (`databases.restore`, admins) and `POST /volumes/backups/{backup}/key`
(`volumes.browse`, admins) need a password (and 2FA) confirmation within the last 5 minutes, return the key as a
`falak-restore` key file, and are recorded in the audit log (`databases.backup_key_exported`,
`volumes.backup_key_exported`). Whoever holds the key file and the object can read the backup.

## `falak-restore`: restoring without Falak

A static binary published with each release (`falak-restore-{linux,darwin}-{amd64,arm64}`, in `SHA256SUMS`).

> **Customer-held backups can be forged.** Their header carries the data key encrypted to your *public* key, so anyone
> who can write to the bucket can produce a file that opens with your identity. Falak checks the stored file's SHA-256
> it recorded on every restore; offline, pass `--expect-sha256 <the backup's plaintext SHA-256>` (shown with the backup)
> — `falak-restore` warns when it is missing for an age-encrypted file. Control-plane-held keys are secret, so only
> Falak (or whoever holds an exported key) can produce a file that opens.

```sh
# Download the object (Download in the backup list, or from your bucket), then:
falak-restore --info backup.sql.zst.fkb                       # key mode and key id (the backup id)
falak-restore --key-file falak-backup-<id>.key --out dump backup.sql.zst.fkb             # cp keys
falak-restore --identity falak-backups.key --out dump backup.sql.zst.fkb                 # customer-held keys
falak-restore --key-file k.key --expect-sha256 <plaintext sha256> --out dump backup.fkb  # also check the recorded hash
```

Then load the plaintext with the engine's tools: `pg_restore -d <db> dump` (PostgreSQL custom format), `mysql <db> <
dump` (MySQL / MariaDB), copy it as `dump.rdb` into a stopped Redis / Valkey, or `tar -xf dump` for a volume.

Exit codes: `0` verified, `1` wrong key or a corrupt / truncated file, `2` usage. With `--out`, nothing is left behind
unless the whole file verified. On stdout, data is written segment by segment as it verifies: discard it when the exit
code is not `0`.

## Restore drills

Per database or volume schedule: `drill` = `off`, `weekly` or `monthly`. The default is `weekly` when the instance
(or, for a volume, a site using it) belongs to a production environment of a project, `off` otherwise. Drills run
from `RunDueDrills` / `RunDueVolumeDrills` (every 10 minutes, claimed like backups), or now with "Drill now".

**Databases (`db.drill`).** The latest successful backup of the schedule's database verified least recently is
restored into a throwaway container: the instance's image **digest**, the instance's memory limit capped at 512 MiB
(`FALAK_DRILL_MEMORY_BYTES`; at least the engine's minimum), one CPU (`FALAK_DRILL_CPUS`), at most 512 processes,
every capability dropped but `CHOWN DAC_OVERRIDE FOWNER SETUID SETGID` (what the official entrypoints need to prepare
the data directory and drop to the engine's user; `images/db/drill-test.sh` checks each image with exactly these),
`no-new-privileges`, `--network none`, no published port, data in `/var/lib/falak/drills/<id>`, a random password
on the tmpfs. Checks:

- the backup downloads, its SHA-256 matches, it decrypts and `falak-db restore logical` succeeds;
- SQL: at least one table; Redis / Valkey: at least one key;
- the row counts of the 10 largest tables (Redis / Valkey: the key count) are within ±10 %
  (`FALAK_DRILL_TOLERANCE_PERCENT`) of the counts `falak-db table-counts` recorded just before the dump (backups of
  schedules with drills record them);
- the optional check query returns at least one row. It must be a single `SELECT`, without `;`, comments or `\`,
  and runs as a count in a read-only transaction on the throwaway copy (`falak-db query`), as a temporary role that
  can only read: PostgreSQL `pg_read_all_data` with `statement_timeout = 60s` and read-only transactions set on the
  role; MySQL / MariaDB a user with `SELECT` on the database and a 60 s statement limit. The role is dropped
  afterwards, and the agent gives up on the query after 75 s whatever the engine does.

The container, its data and its password file are removed whatever happened; what an agent crash leaves behind
(containers labelled `falak.db.drill`, `/var/lib/falak/drills/*`, `<volumes>/.drills/*`, their secret directories)
is swept at the agent's start and every hour once older than 3 hours.

**Volumes (`volume.drill`).** The latest archive is unpacked into `<volumes root>/.drills/<id>` (the same checks as a
restore: checksum, decryption, the tar stream's SHA-256, entries confined to the directory), the file count is compared
with the archive's, and the directory is removed.

**Result.** Each drill is kept (`databases_drills`, `volumes_drills`): `passed`, `failed` or `skipped`, its checks,
duration and an **RTO estimate** (download + restore time). A passed drill marks the backup *verified*. A failed one
alerts (`databases.drill_failed`, `volumes.drill_failed`, critical; a later pass resolves it). A drill is `skipped`
when there is no backup yet, the keys are customer-held, the agent is offline, or the server lacks the room: the agent
checks `MemAvailable` (the drill's memory + 256 MiB) and free disk (3× the dump + 512 MiB for the data, the file for
the download) before pulling anything. Pick a **drill server** (another server of the organization) on the schedule
to run drills there instead. A drill server receives the restored data, so choosing or changing it takes the restore
permission (admins; volumes: the browse permission), like restoring does.

## Pruning and older backups

Retention is unchanged (count and age per schedule; the newest successful backup is always kept). Backups taken
before encryption (v0.10.0-rc.1 and earlier) keep their rows but are no longer restorable from Falak.

## What to keep in mind

- Lose a customer-held identity and its backups are gone for good: Falak can't help.
- `cp` keys live in the control plane's database, sealed under the KEK: back up the KEK with the database
  (`docs/INSTALL.md`), or a database backup can't open its backups' keys.
- Point-in-time recovery (v0.10 step 5) ships WAL and binlog segments as FKB1 files the same way.
